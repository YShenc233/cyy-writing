# CYY 小陈公众号文章工作流

## 两条创作路线

- **主题调研**：用户提供主题，由代理调研可靠资料、核实事实、选取案例与图片/GIF，独立组织文章，用 CYY 小陈风格写作。不要求用户先提供参考文章。
- **模板改写**：用户提供模板、参考文章或文件，先读取实际内容与内嵌媒体，识别模板的骨架、信息价值及明确要求保留的栏目；把表达改成用户的 CYY 小陈风格。模板作为结构参考，明确要求保留的结构优先；补充的事实仍需核实，不能沿用模板中不适用于新主题的旧数据。模板媒体先提取并核对是否适合新文，再决定保留或替换。

用户同时提供主题与模板时，围绕主题调研并按模板组织；两条路线共用下面的交稿和修改流程。

## 共同交付顺序

1. **先交图文 Markdown**：内部完成调研、写作、Humanize 和媒体整理。AI 主题两条路线都先完成下述 X 案例环节及其交稿检查。第一遍交付一份可编辑 `.md`，其中同时包含完整文章和插在对应段落的图片、GIF；附保持目录关系的 ZIP。此阶段不生成 HTML。
2. **等待用户修改**：交稿后结束当前写作阶段，让用户在 Markdown、Notion 或聊天中修改。收到修改意见时更新同一份 Markdown 与媒体引用；继续交付 Markdown，不自动排版。
3. **取得最新定稿**：用户明确说修改完成、定稿或要求生成 HTML 后，重新读取用户修改的文件/Notion 页面。最新修改稿是排版来源，不使用旧聊天正文或旧草稿覆盖它。若用户同时改了多个版本且冲突，先确定采用哪个版本；保留用户新加的图片/GIF和顺序。
4. **再生成 HTML**：以最新定稿生成公众号内联样式 HTML，保留原图文顺序。检查正文与定稿一致、图片路径可解析、GIF仍有动画帧。更新原 Markdown、本地文件和同一 Notion 页面。

“保存”“上传 Notion”“同步”只保存当前 Markdown 阶段内容，不等于允许生成 HTML。第一遍即使用户要演示完整工作流，也先完成 Markdown 交付；只有用户明确要求本轮同时排版才跳过等待。

## Markdown 与媒体交付

- 每篇一个目录，按用户偏好命名为 `YYYY.MM.DD-公众号标题`。新稿使用用户当地写作日期，旧稿沿用原日期。用户已指定本地根目录时沿用；否则放任务可交付输出目录。首轮不因保存位置缺失而延迟交稿。
- 本地正文以 `最终版.md` 作为持续更新的主文件，媒体保存在同目录的 `images/`，示例：`![模型能力演示](images/demo.gif)`。第一遍主 Markdown 本身必须有图片/GIF引用，不能只把媒体放进附件、单独说明文件或 Notion。
- 首轮先整理实际媒体，再交稿；需要 GIF 时取得真实动画或从实际录像截取，不把单帧 `.gif` 当作动画，不为凑素材制作与主题无关的流程动画。教学示意仅在用户要求时另行清楚标注。
- 图片/GIF具有说明文字，按需记录来源、获取日期和处理方式。模板内嵌媒体提取后也加入 `images/`。无法取得必要素材时交付已经取得的素材并明确缺失项，不能以“图片”占位冒充已嵌入。
- 修复旧稿时读取用户指出的实际文件，修改该稿件的媒体引用；分别验证该 Markdown 和已有 HTML，不用另一篇示例的成功替代验证。
- 验证主 Markdown 每个本地媒体引用都指向存在且能解码的文件；检查需要动画的 GIF 帧数大于 1。用可用 Markdown 预览检查图片和动画，无法检查时说明验证范围。
- Markdown 使用文件引用而非自带二进制图片。因此交付 `最终版.md` 与 `images/` 的 ZIP，移动或导入时保留相对目录。若聊天/应用预览不能解析相对路径，在展示预览时使用实际输出媒体的绝对路径；不要因此改坏可搬运文件里的相对路径。首轮回复给出 Markdown 和素材包链接，按用户需要展示正文或图文预览。
- 用户自行添加图片/GIF时，只需把文件放进 `images/` 并在正文对应段落插入引用；或直接在 Notion 插入媒体。后续排版前重新读取这些修改，不漏掉用户新素材。
- 只更新同一稿件，不积累原始稿、Humanize 中间稿或多个版本目录。第一遍 ZIP 包含 Markdown、媒体和来源记录，定稿后才加入 HTML。

目录示例：

```text
YYYY.MM.DD-公众号标题/
├── 最终版.md
├── images/
│   ├── cover.png
│   └── demo.gif
├── 来源记录.json
└── 最终排版版.html    # 仅用户修改定稿后生成
```

## Notion 与本地保存

沿用用户已授权的 `memory/notion-destinations.json` 中的工作空间与父页面；本地根目录优先本次明确指定，其次读取该记忆中的 `localRoot` 或 `memory/save-roots.json` 的历史授权位置。未指定的 Notion 目标在图文交稿后再确定。

默认将当阶段的文章和实际交付物保存到 Notion。第一遍只归档图文 Markdown、媒体、来源记录与素材包，标记待修改；定稿后更新同一页面并加入 HTML。用户选择仅本地时跳过 Notion。实际归档或读取用户在 Notion 修改的稿件时，读取 [references/notion-archive.md](references/notion-archive.md)。

## 写作与核实

只生成一个 CYY 小陈风格版本，沿用用户给定标题。以核心判断组织文章，用案例帮助读者选择；首轮不先交风格分析或提纲代替文章。用户明确要求一步一步演示时，在进度消息展示各步结果。

## AI 新模型文章的默认要求

- **读者与目标**：同时面向使用 AI 写代码的人和希望提高日常工作效率的人。读者看完应能判断值不值得试，并知道第一步怎么用。技术术语首次出现时用一句话解释；按主题选择编程与办公案例，不机械地平均分配篇幅。
- **先查对应官网**：写新模型介绍时，实际访问开发商的官方发布文章，并按内容需要查看官方模型说明、价格页和评测说明。核实准确型号、发布日期、开放入口、订阅与 API 费用、上下文和关键能力。用户参考稿中的数字也需要核对；缺少可靠来源时不把它写成已确认事实。
- **配图与正文一起成稿**：查官网时主动寻找值得截图的 benchmark 排名、能力对比图、价格表、成本对比图及产品演示。选取能支撑文章判断的图，不要求每篇固定张数。第一版 Markdown 尽量直接嵌入已收集的本地素材，不等正文定稿后才找图。
- **X 案例与效果展示是交稿环节**：AI 主题调研和模板改写都必须实际搜索 X，并读取 [references/x-case-workflow.md](references/x-case-workflow.md)。围绕文章的能力判断查找原帖与真实成品，把取得的截图或演示 GIF 插入相关章节，说明任务、结果和观察点。交稿前按该参考检查案例与媒体；只有榜单、宣传图、调侃动画或原帖链接时，效果展示仍未完成。找不到可核实案例或取不到媒体时，明确报告缺口并收窄正文结论。
- **截图保留解释条件**：截取真实页面或官方原图，保留模型名称、坐标、单位、图例和影响结论的脚注。确认截图清晰可读；解释官方评测的测试条件，不将厂商图表直接称为独立排名。不同推理档位、缓存规则或测试条件下的数据不能直接合并比较。自制价格图需注明数据来源和换算口径，不能冒充官网截图。
- **案例用于帮助选择**：讲清任务、完成结果与不足，再给出适用场景。优先选择能展示真实成品的案例；有视频时可截取有代表性的 GIF，每张图配一句读者应关注的地方。区分官方演示、社区体验和作者亲测，不将别人的测试写成“我们实测”。静态图片制作的轮播需如实标注。
- **写作顺序与判断**：先确定文章的核心判断，再挑选证据和素材，围绕它组织正文。开头尽快交代谁值得试、为什么；标题与正文兑现同一主题。跑分用来支撑具体用途，价格区分 API 单价、订阅额度和完成任务的实际成本。结尾给一个读者可以尝试的小任务或明确的选择方法。
- **来源记录与素材交付**：图片和 GIF 保存到文章的 `images/` 目录，Markdown 与 HTML 使用可解析的本地引用。将来源 URL、获取日期、关键测试条件及裁剪/轮播等处理方式保存在工作素材记录中。用户偏好正文直接展示素材，不默认插入“原帖”文字超链接。找不到媒体或无法访问官网时如实说明，不以无关素材代替。


## CYY 小陈写作风格

#### 写作规范

**开头**

- 固定开场身份句：`大家好，我是CYY小陈。`
- 前 5 段内必须交代：
  - 今天要聊什么。
  - 为什么这个话题值得关注。
  - 读者看完能获得什么。
- 可以加入轻松吐槽、反问或个人判断。

**语气**

- 像程序员朋友在分享经验，不要官方腔。
- 多用「我」「你」「大家」。
- 可以自然使用这些表达：好家伙、不是哥们、嘎嘎快、不要太方便、一把梭、开箱即用、拉了、GG、真香、省心、最后哔哔。
- 不要使用低俗、夸张营销号、强行煽动情绪的表达。

**结构**

- 使用清晰小标题。
- 教程类文章优先用步骤结构：准备工作 -> 开始实战 -> 测试验证 -> 踩坑和解决 -> 最后总结。
- 测评类文章优先用对比结构：背景 -> 参赛选手 -> 测试任务 -> 结果展示 -> 优缺点 -> 选择建议。
- 每个技术概念都要讲人话，可以加类比。

**段落节奏**

- 短段落为主。
- 重要观点单独成段。
- 不要大段堆信息。
- 优先在对应段落嵌入已核实的配图；尚未取得的必要素材可保留清楚的图片占位，并说明缺少什么。

**内容处理**

- 模板改写保留核实后的核心事实，主题调研围绕可靠资料组织判断。
- 按主题重组叙事；用户明确要求保留的模板结构和栏目优先。
- 改写所有句子，不要连续复用原文表达。
- 可以补充解释、过渡、个人体验和读者建议。
- 如果原文信息不足，可以用更自然的表达补齐逻辑，但不要编造具体数据。

**结尾**

- 使用「最后哔哔」或类似轻松收束。
- 总结核心观点。
- 给读者明确建议。
- 固定结尾品牌句：

```text
小陈持续分享 AI 编程干货。觉得有用的话记得点赞收藏和关注，也欢迎在评论区聊聊：你现在是怎么用 XX 的？
```


## Humanize

交稿前调整句式长短，使用自然口语和具体场景，避免模板化过渡与重复总结；个人判断可以明确表达，别人的测试不能写成作者亲测。

## 定稿 HTML

使用 [assets/wechat-template.html](assets/wechat-template.html) 或当前可用排版能力，样式全部内联，无外部 CSS、字体和脚本，保留定稿的图文顺序及 GIF 引用。用当前定稿生成 `最终排版版.html`，用户未修改定稿前不生成。用于本地阅读的 HTML 优先内嵌图片和 GIF，使单个文件可离线打开；使用相对路径时附完整素材包并说明目录要求。检查实际渲染的图片数量、段落位置及 GIF 动画。公众号粘贴后仍需确认媒体是否导入，未导入时单独上传。

定稿交付给出 Markdown、HTML、素材包和 Notion 链接（如已保存）。复制指南：浏览器打开 HTML → 全选复制 → 粘贴到公众号编辑器；未随粘贴导入的媒体单独上传。首轮交付只给 Markdown 阶段产物和修改说明，不提前发送 HTML 链接或复制指南。
